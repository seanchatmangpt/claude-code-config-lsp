# Analysis of `claude-code-config-lsp` Codebase

**Summary**: This analysis explores the codebase structure of the `claude-code-config-lsp` workspace. It documents the current argument parsing entrypoints, conformance and coverage score definitions, cryptographic receipt chain foundation, and diagnostic analyzer flow, identifying gaps where the planned CLI commands (`conformance`, `receipt verify`, `receipt chain`, `fix`) need to be integrated.

---

## 1. CLI Argument Parsing

### Binary Entrypoint (`src/main.rs`)
The binary entrypoint is located at `src/main.rs`. 
- **Bare Invocation (No Arguments)**: If the binary is invoked without arguments (`std::env::args().nth(1).is_none()`), it starts the LSP server over `stdio` within a newly built Tokio runtime (`nouns::config::start_stdio_server()`). This is designed to support LSP clients (e.g., Claude Code, editors) spawning the server directly.
- **Invocation with Arguments**: If arguments are present, the entrypoint delegates to `clap_noun_verb::run()`, which provides synchronous noun-verb routing.

```rust
fn main() -> clap_noun_verb::Result<()> {
    if std::env::args().nth(1).is_none() {
        let rt = tokio::runtime::Runtime::new().expect("failed to build tokio runtime");
        rt.block_on(nouns::config::start_stdio_server());
        return Ok(());
    }
    clap_noun_verb::run()
}
```

### Verb Registration (`src/nouns/config.rs`)
Verbs are declared in `src/nouns/config.rs` using the `#[verb("verb_name", "root")]` macro attribute from the `clap-noun-verb-macros` crate. The macro uses `linkme` under the hood to register these verbs.
Currently defined verbs in the codebase:
- **`serve`**: Runs the LSP server over stdio (requires `--stdio` flag).
- **`scan`**: Recursively scans a workspace directory (defaults to `.`) and lists all config diagnostics.
- **`export`**: Serializes every Claude Code configuration file in a workspace into a JSON tree (`ConfigTree`).
- **`unused`**: Performs a "dead-config" audit of a workspace and returns a `ConfigUsageReport`.

## 2. Conformance Score

### Current Codebase State
There is currently **no workspace conformance score** (such as the `WorkspaceConformance` JSON report described in `docs/tutorial.md`) calculated or defined in the Rust source code.
Currently implemented metrics:
1. **LSP Method Coverage Score** (`src/coverage.rs`):
   - Computes the percentage of LSP methods implemented by the server, derived from the server's `ConformanceVector` (defined in `src/conformance.rs`).
   - Sourced via `coverage_report()`, which calculates `CoverageReport::coverage_percent`.
2. **Unused Configuration Metric** (`src/inventory.rs`):
   - Computes the proportion of orphaned or declared-but-missing configuration items in a workspace (`ConfigUsageReport::unused_percent`).

### Health Virtual Document (`claude-config://health`)
Although `docs/tutorial.md` states that requesting `claude-config://health` returns a JSON representation of `WorkspaceConformance` (with `score`, `surfaces_checked`, `surfaces_admitted`, and a list of `violations`), the current implementation in `src/virtual_docs.rs` and `src/backend.rs` is a placeholder that renders the markdown fragment from `CoverageReport` (LSP method coverage) rather than workspace configuration compliance.

## 3. Receipt Chain

### Configuration Snapshot Receipts
Receipts are implemented inside the `praxis` crate (`praxis/src/lib.rs`):
- **`Evidence<T, S, E>`**: A wrapper structure containing the conformance data (`T`), status markers (`S`), extension markers (`E`), and an RFC3339 UTC timestamp.
- **`AdmittedReceipt`**: Created via `AdmittedReceipt::sign(evidence)`, which serializes the `Evidence` object into JSON, computes its `blake3` hex hash, and populates the receipt fields (`hash`, `timestamp`, `verdict = "ADMITTED"`, `proof = "praxis::admit[v1]"`).

### Integration in LSP Backend (`src/backend.rs`)
The LSP server implements a workspace command handler for `"claude-code-config/conformanceAudit"`:
1. It triggers `praxis_retrofit::audit_workspace()` (which returns a stubbed `AuditResult`).
2. It fetches `crate::conformance::conformance_vector()`, wraps it as `Evidence`, and signs it to produce an `AdmittedReceipt` using `blake3`.
3. It emits a compliance event log entry and returns the `AdmittedReceipt` serialized to JSON.

### Code Locations
- **Receipt Structures**: `praxis/src/lib.rs`
- **Workspace Auditing Stub**: `praxis-retrofit/src/lib.rs`
- **Command Handling and Hashing**: `src/backend.rs` (lines 250-279)

### Gaps
There is currently **no implementation of a Merkle chain validation**, chain persistence to `~/.claude/receipts/`, or file-integrity verification in the codebase. The `previous_receipt_hash` chain mechanism is only illustrated in mock JSON files under `.ggen/receipts/` generated by `ggen sync` and must be implemented for CLI commands.

## 4. Diagnostics & Auto-Fixes

### Diagnostics Flow (`src/scan.rs`)
Diagnostics are analyzed and reported via `analyze_document` in `src/scan.rs`:
1. **Classification**: Path or URI is checked against `classify(uri_or_path)` to determine the configuration surface type (`"skill" | "claude_md" | "agent" | "json" | "toml" | "hook" | "unknown"`).
2. **Analysis Dispatch**: Based on the classification, the file is run through corresponding analyzers defined in `src/analyzers/`:
   - `claude_md::validate_claude_md` (verifies section structure of `CLAUDE.md` and `agents.md`).
   - `frontmatter::validate_agent_frontmatter` & `FrontmatterAnalyzer` (validates agent definition blocks).
   - `hook::HookAnalyzer` (analyzes shebang and validity of hook scripts).
   - `json::JsonAnalyzer` & custom functions (checks deprecated keys, hook event names, and schema compliance in `plugin.json` and `settings.json`).
   - `toml::TomlAnalyzer` (checks CalVer and edition keys).
3. **Pattern Matching**: The analyzers search for pattern matches using either naive substring lookups or SIMD-accelerated matching via `bcinr_logic::swar_str` if the optional `bcinr` feature is enabled.

### Auto-Fixes
There is currently **no auto-fix or repair implementation** in the codebase.
- The `textDocument/codeAction` method is explicitly refused in the server's conformance vector (`src/conformance.rs` line 24), meaning the LSP server does not advertise code actions to the client.
- No Rust modules exist to perform string replacements or automated modifications to configuration files.
